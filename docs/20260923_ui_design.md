# ローカル GUI の設計

作成日: 2026-09-23

---

## 1. 方針

`collect` で集めた結果の確認と、PCに残らない作業・変化・判断の記録を、ブラウザから行う。

- **標準ライブラリのみ**（`http.server`）。追加インストール不要という原則を崩さない
- **UI にロジックを持たせない**。既存 API（`ManualInput` / 各 `Repository`）を呼ぶ薄い層に留める
- CLI と GUI は同じ状態を見る（実行中の作業は `meta` テーブルの `manual_running`）
- **手動起動**。常駐・自動起動はしない
- 過去日の閲覧・編集に対応する

将来、常駐が必要になった場合は同じ HTML を `pywebview` でラップできる構成にしておく。

---

## 2. 起動

```powershell
python app/cf.py ui                 # 既定 http://127.0.0.1:8765 を開く
python app/cf.py ui --port 9000     # ポート変更
python app/cf.py ui --no-browser    # ブラウザを自動で開かない
```

- **`127.0.0.1` 固定でバインドする**（`0.0.0.0` にしない）
- 起動時にトークンを生成し、URL に含めて開く。以降の書き込み要求はトークン必須
- Ctrl+C で終了

### 俯瞰図（縦軸=案件・種別、横軸=時間）

タイムラインの一覧の**上**に、1日を見渡すための表を出す。

- **縦軸** … 案件 × 種別の組み合わせ。その日に記録がある組み合わせだけを出す
- **横軸** … 時間。その日に記録がある時間帯だけを出す（9時始まりの日は 9 から）
- **セル** … その刻みのうち何分を占めたかで濃さが変わる。1分でも記録があれば見える濃さにする
- **右端** … その組み合わせの合計時間

刻みは **1時間 / 30分 / 5分** から選ぶ（既定は1時間）。日付を切り替えても選んだ刻みは変わらない。

| 刻み | 1時間あたりの列 | セル幅 | 用途 |
| --- | --- | --- | --- |
| 1時間 | 1 | 20px | 1日の流れをざっと見る |
| 30分 | 2 | 12px | 午前・午後の使い方を見る |
| 5分 | 12 | 6px | 細切れの作業・中断を見る |

**列見出しは刻みによらず「時」単位**で、細かい刻みのときは `colspan` でその時間ぶんをまとめる。
時の変わり目には区切り線を入れ、5分刻みでも何時ごろか追えるようにする。

#### 行の並び

**設定の並び順 / 合計時間順**から選ぶ（既定は設定の並び順）。

| 並び | 内容 | 向いている用途 |
| --- | --- | --- |
| 設定の並び順（既定） | 設定画面で決めた案件順・種別順に従う | 日をまたいで同じ位置で比べる。ドロップダウンや選択肢と並びの根拠が揃う |
| 合計時間順 | その日の合計時間が多い順 | その日に何へ時間を使ったかを上から見る |

いずれの並びでも、次の扱いは共通。

- **案件が未指定の行は最後**
- 設定に無い案件・種別（隠した後も記録が残っている場合など）は、設定にあるものの**後ろ**
- 合計時間順で同点の行は、設定の並び順で決める（同点で並びがぶれないようにするため）

セルにカーソルを置くと `09:00-10:00　sample_project / コーディング　60分` が出る。
横に長くなるため、表は枠の中で**横スクロール**する。行見出し（案件 / 種別）はスクロールしても残す。

記録が1件も無い日は表ごと出さない。
前日から続く行・翌日へ続く行は、その日の 0:00 / 24:00 で切って数える。

材料はタイムラインと同じ1つの層（確定があれば確定、無ければ観測→手入力→予定）。
一覧が集約後の行を出すのに対し、こちらは案件・種別だけで束ねる（タスクは見ない）。

### タイムラインの表示

各行は **`開始-終了　案件 / 種別 / タスク / 情報源`**。案件・種別・タスクの順はほかの箇所と揃える。
案件が無ければ `（未指定）`、タスクが無ければ `-` を出して桁を保つ。

**固定の高さ（320px）の中で縦スクロールする。** 1日ぶんの行数で画面が下へ伸び続けると、
その下にある変化・判断・現在の状態へ届かなくなるため。生ログ一覧と同じ扱い。

#### 同じ内容が続く行はまとめる

**案件・種別・タスクが同じ行が続いていれば、開始〜終了を合わせて1行にする。**
まとめた行には件数を添える（`sample_project / コーディング / 設計 / windows / 3件`）。
情報源が混ざる場合は `windows+manual` のように並べる。

まとめない条件は2つ。

| 条件 | 理由 |
| --- | --- |
| 時間が離れている（直前の行の終わりに接していない） | 空いていた事実が消えるため。空白行をはさむ場合も同じ |
| **編集できる行（手入力・`reported`）** | まとめると、まとまった行から個別の記録を編集・削除できなくなるため |

タイムラインは1つの層だけを出す（確定があれば確定、無ければ観測→手入力→予定）。
そのため実際には、**`build` 済みの日は全体がまとまり、確定前の手入力だけの日は1件ずつ出る**。
`[タイムラインを作り直す]` を押すとまとまった表示に変わる。

### 予定の分類

「タイムライン」カードの**直後**に「予定の分類」カードを置く。予定が1件も無ければカードごと出さない。

```
├─ 予定の分類 ───────────────────────────────────┤
│ 9/23〜9/30 の予定 3件（未分類 2件）                         │
│ 9/24 10:00〜9/26 11:00・3回  設計レビュー （未分類）[種別▼] │
│ 9/24 09:00                  朝会         [会議  ▼][解除]  │
```

- 未分類の行は目印を付けて先頭に並べる
- 種別を選ぶと即座に保存し、画面全体を取り直す（タイムラインと俯瞰図にも効くため）
- 分類済みの行には `[解除]` を置く
- 件数が多いと縦に伸びるため、固定の高さ（320px）で縦スクロールする
- `uid` が無い予定がある場合は、その件数と理由を出す

### 入力を減らす仕掛け

| 仕掛け | 意図 |
| --- | --- |
| 空白区間をクリックすると開始・終了が埋まった補完フォームが開く | 「後から補完」で最も面倒な時刻入力をなくす |
| 案件はドロップダウン（`ContextRepo.projects()` から生成） | 案件名の表記ゆれ・suffix 不一致を防ぐ |
| 種別もドロップダウン（`ActivityType`） | 不正値を入れられない |
| 日付は前日・翌日・今日のボタンで移動 | 過去日の閲覧・編集を最短操作で |

### 収集・記録の状態表示

画面上部に、いま何が動いているのかを常に出す。

| 表示 | 判断材料 |
| --- | --- |
| `生ログ収集：収集中 / 停止中` | 収集側が毎回更新する心拍（meta の `collector_heartbeat`） |
| `最終取得 HH:MM / <日付> の生ログ N件` | `raw_events` の最終時刻と件数 |
| `作業記録：記録中 / なし` | `meta` の `manual_running` |

**心拍で判断し、生ログの最終時刻では判断しない。**
生ログは `flush_every` 件ごとのまとめ書きなので、最後の1件では
最大 `flush_every × interval` 秒ぶん古く見え、「開始直後なのに停止中」
「終了済みなのに収集中」の両方を起こすため。収集は終了時に心拍を消すので、停止は即座に反映される。

収集中でも件数はまとめ書きの周期でしか増えない。誤解しないよう
`N件ごとに保存` を添える。停止中で当日を見ているときは、始め方
（`python app/cf.py collect`）を出す。

#### 作業記録の行

生ログ収集の行と同じ密度で、作業記録の行にも内容を出す。行が常に意味を持つよう、
記録中・停止中のどちらでも内容つきで出す（生ログ収集が停止中でも件数を出しているのと同じ考え方）。

**表現は生ログ収集の行と揃える。** 動いているかどうかを `〜中` と `停止中` の対で表し、
片方だけ `なし` のような別の言い方をしない。件数の呼び方も行の見出しに合わせる。

| | 動作中 | 停止中 | 読み込み前 | 件数の呼び方 |
| --- | --- | --- | --- | --- |
| 生ログ収集 | `収集中（5秒間隔）` | `停止中` | `確認中` | `9/23 の生ログ 17件` |
| 作業記録 | `記録中` | `停止中` | `確認中` | `9/23 の作業記録 2件` |

操作ボタンの名前も対にする。

| | 開始 | 停止 |
| --- | --- | --- |
| 生ログ収集 | `[収集を開始]` | `[収集を停止]` |
| 作業記録 | `[記録を開始]` | `[記録を停止]` |

操作後のメッセージも同じ語で揃える（`記録を開始した` / `記録を停止した（1h 30m）`）。

作業記録のボタンは**1つだけ**で、記録中かどうかで文言と動作が入れ替わる。
**位置は動かさない。** 記録中は案件・種別・タスクの入力欄を**非活性**にする（隠さない）。

入力欄は**案件・種別・タスクの順**に並べる。案件を先に決めてから種別を選ぶ流れに合わせる。
タイムライン・状態表示・現在の状態カードなど、この3つを並べて出す箇所はすべて同じ順にする。

非活性の入力欄には、**記録中の内容を入れる**。空のまま非活性にすると、
画面を再読み込みしたときに選択肢の既定値が残り、
「帯は会議、入力欄は開発」のように食い違うため。値の出どころは `renderRunning()` に一本化する。

ボタンの出し分けも揃える。**どちらも「今できる操作」だけを出す。**

| 状態 | 生ログ収集 | 作業記録 |
| --- | --- | --- |
| 動作中 | `[収集を停止]` | `[記録を停止]`（入力欄は非活性） |
| 停止中 | `[収集を開始]` | `[案件▼][種別▼][タスク___] [記録を開始]` |
| 別プロセスが収集中 | `[収集を停止]`（無効）＋ 別ウィンドウで収集中の案内 | 該当なし |
| **確認中（通信失敗）** | **両方とも隠す** | **操作欄ごと隠す** |

確認中に操作欄を出さないのは、記録中かどうかが分からない以上、
ボタンを `記録を開始` と `記録を停止` のどちらにすべきかも決められないため。

タイムライン・変化・判断は確認中でも消さない。これらは記録済みの内容で、
勝手に変わるものではないため、古いまま残っても誤解を招かない。
隠すのは「今の状態」を述べる表示と、それに対する操作だけ。

過去日を表示中の補足も揃える（`収集中（5秒間隔・今日の状態）` / `記録中（今日の状態）`）。

`確認中` は「まだ分かっていない」を表す。`停止中` は「問い合わせた結果、動いていないと分かった」。
**通信に失敗したときは `確認中` へ戻す。** 取得できた最後の値を出し続けると、
実際には止まっているのに「収集中」と表示し続けることになるため。
状態が分からない間は、開始・停止のボタンと案内も出さない（正しい操作を提示できないため）。
30秒ごとの経過更新も、この間は書き戻さない（`確認中` を上書きしてしまうため）。

記録中:

```
● 作業記録：記録中   sample_project　/　会議　/　要件整理　/　開始 14:20　/　経過 33m
```

停止中:

```
○ 作業記録：停止中   9/23 の作業記録 2件　/　最後 11:00
```

**内容の出どころは、この帯1か所に限る。** 操作欄はボタン1つだけを置く
（案件・種別・タスク・経過はもちろん、`● 作業中` のような状態表示も置かない。
真上の帯が `作業記録：記録中` を出しているため）。同じことを2か所に出すと、
書式（`1h 30m` と `33分経過`）や更新漏れでずれる。**帯＝状態、カード＝操作**と役割を分ける。

- 経過は30秒ごとに更新する（再読み込み不要）。既存の `updateElapsed()` を拡張
- **経過8時間以上で止め忘れの警告を出す**（`8時間以上 記録中。止め忘れの可能性`）

#### 日をまたぐ記録の分割

`ManualInput.stop()` / `add()` は日境界（00:00）ごとに区間を分割して複数の Activity として保存する。
`ActivityRepository.list_between` が `start_at` だけで絞り込むため、分割しないと日をまたぐ記録が
終了日側の一覧・時間集計から抜け落ちる（実測: 前日23:50開始→当日00:10終了が、以前は当日0件）。
分割の各区間は同じ `activity_type` / `project` / `task` / `layer=reported` / `source=manual` / `confidence=1.0`。
日をまたがない通常ケースは今までどおり1件。カレンダーの `.ics` で日をまたぐ予定を分割しているのと同じ考え方。

#### 表示中の日と「今」の齟齬をなくす

収集も作業記録も「今」動いているかどうかで、常に**今日**に対して記録される。
一方で画面は過去日も表示できるため、区別しないと「見ている日が収集・記録されている」と誤解する。

| 直した点 | 内容 |
| --- | --- |
| 件数に日付を明示 | `この日 17 件` → `9/20 の生ログ 17件`。手入力の件数も同じ形 |
| 最終取得の日付 | `collector.last_event_at` は収集全体の最終時刻。表示中の日と違えば `9/23 05:53` のように日付を添える |
| 今日の状態であることを明示 | 過去日表示中は `生ログ収集：収集中（5秒間隔・今日の状態）` / `作業記録：記録中（今日の状態）` |
| 記録先の明示 | 過去日表示中で収集・記録のどちらかが動いていれば `収集・記録は今日に対して動く。開始・停止すると今日に記録される` を出す |
| 操作欄の注記 | 過去日表示中は `（今日の記録。停止すると今日に記録される）` を出す |

#### 終了・開始メッセージの出し分け

以前は結果によらず常に同じ文言だったため、実際の結果に合わせて出し分ける。

| 操作・結果 | メッセージ |
| --- | --- |
| `work stop`（実行中なし） | `実行中の作業なし` |
| `work stop`（開始直後の取り消し） | `開始直後のため記録せず取り消した` |
| `work stop`（通常） | `作業を終了した（1h 30m）` |
| `work stop`（日をまたいだ分割） | `作業を終了した（20m）　日をまたぐため2件に分割` |
| `work start`（実行中の記録を自動で止めて開始） | `前の記録（開発）を停止して開始した` |

種別の日本語ラベルは画面側で変換する。API（`stopped_type`）が返すのは値のみ。

### 収集の開始・停止

`python app/cf.py collect` と同等の収集を、状態表示の帯にあるボタンから操作する。

**UI プロセス内のバックグラウンドスレッドで動かす。** 別プロセスは起こさない
（プロセス管理・孤児プロセスを避けるため）。そのぶん **UI を終了すると収集も止まる**。
収集中はその旨を画面に出し、終日動かすなら CLI を使うよう促す。

| 状態 | 表示 |
| --- | --- |
| 停止中 | `[収集を開始]` |
| この UI が収集中（`owned_by_ui=true`） | `[収集を停止]` |
| 別プロセスが収集中（`owned_by_ui=false`） | ボタンを無効化し「別のウィンドウで収集中」 |

**二重起動を防ぐ**のが要点。心拍が生きている間は別プロセスが収集中とみなし、
開始を 409 で拒否する。生ログが重複して時間集計が壊れるのを避けるため。

収集スレッドは**スレッド内で `Database` を開く**（sqlite の接続はスレッド固有のため）。
UI 終了時（`serve()` の finally）に必ず停止させ、心拍を残さない。

### 生ログの扱い

**既定では表示しない。** ウィンドウタイトルに顧客名・メール件名が入りうるため、
画面共有時の事故を避ける。`[生ログを表示]` を押したときだけ、その区間の生ログを取得して開く。

| 仕様 | 内容 |
| --- | --- |
| 集約 | **連続する同一内容（process + window_title）を1行にまとめる**。`14:49-14:52 python.exe … (3件)` |
| 表示領域 | **固定の高さ＋スクロール**。1日で数千件になるため、画面を占有させない |
| 最新の反映 | 開いた状態で再読み込みすると取り直す。今日かつ収集中なら末尾（最新）へスクロール |
| 収集中の鮮度 | 収集側が `flush_max_wait_sec`（既定10秒）で書き出すため、収集中でも直近が見られる |

#### 集約の規則

1サンプル＝1行だと5秒間隔で1日数千行になるため、**直前の行と `process` と `window_title` が
同じなら同じ行にまとめる**。

**時間の空きでは区切らない。** 収集が断続的（PC を離れていた・collect を止めていた）でも
1行にまとまる。そのぶん**件数を必ず表示**し、時間の幅に対して件数が少なければ
途切れていたと分かるようにする。

厳密な区間分割は `sessionize`（`merge_gap_sec` で切る）と `gaps` が担当する。
ここはあくまで生ログを読むための表示であり、集計には使わない。

### 生ログと案件・種別・タスクの紐づけ

生ログの行を選び、その時間帯を活動として記録できる。

| 操作 | 内容 |
| --- | --- |
| 行（集約後）をクリック | 選択を切り替え |
| Shift + クリック | 直前に選んだ行から今の行までをまとめて選択 |
| `[選択した生ログを記録]` | 記録フォームを開く。開始＝最初の行の開始、終了＝最後の行の終了 ＋ 採取間隔 |

案件・種別・タスクは利用者が選ぶ。**ウィンドウタイトルをフォームへ自動で入れない**
（活動の summary は日次サマリへ出力されるため）。

0件のときは空欄にせず、「この日の生ログは0件」と理由の見当（収集が動いていない可能性）を出す。
空欄のままだと、壊れているのか本当に無いのかが区別できないため。

### 編集できるもの・できないもの

| 対象 | 編集 | 理由 |
| --- | --- | --- |
| 手入力の活動（layer=REPORTED） | できる | 本人が入力したもの |
| 空白時間の推定（source=SYSTEM） | できる | AI推定。人が直せるべき |
| PCログ由来（layer=OBSERVED） | できない | `sessionize` の生成物。直しても `build` で作り直される |
| 予定（layer=PLANNED） | できない | カレンダーが正本 |
| 確定（layer=CONFIRMED） | できない | `build` の生成物 |

編集後は `[タイムラインを作り直す]`（`build_day`）を押して確定層へ反映する。
ボタンの文言に内部の層名（確定）を出さない。押す側は「反映されていない表示を直すもの」として扱えればよい。

### 現在の状態

`[今の状態をまとめる]` を押すと `python app/cf.py state` と同じ処理（集計＋保存）が走る。

- 日付ナビに追従し、**過去日は保存済みのスナップショットを参照できる**
- まとめていない日は「この日の状態はまだまとめていない。」と出す
- 時間の材料は確定層のタイムライン。記録を足した後は、先に `[タイムラインを作り直す]` を押す
- 判断エンジン（`decide` / `plan`）へ渡るのはこの内容。渡す際は許可リストで絞られ、ウィンドウタイトル等は渡らない
- **「タスク」の行の直後に「過去7日」「今後7日」を出す。** 過去は日ごとの確定→観測の判定、
  今後は `planned` を直接読んだ予定・締切
  - 予定は最大5件（超過分は `ほか N件`）、締切は最大3件。`blocked` の行には `待ち` を添える
  - 過去に記録が無ければ `記録なし`、予定も締切も無ければ `予定なし` と出す

#### 判断・計画

`[判断する]`（`POST /api/decide`）/ `[計画を作る]`（`POST /api/plan`）を、現在の状態カードの
「判断・計画」から実行する。

- **材料は、押した時点で組み立て直した state。** 押すとまず `[今の状態をまとめる]` と同じ処理
  （組み立て＋保存）が走り、**保存したうえで**その state を材料に判断する。
  画面の「現在の状態」カードに出ている内容と、判断に使った材料が一致する。
  保存済みスナップショットを読む案も検討したが、JSON から `CurrentState` を復元する関数が無く、
  新設すると `to_jsonable` との二重管理になるため採らなかった
- 質問セットは `[next_action▼]` から選ぶ。選択肢は `next_action` / `gap_fill` / `task_triage` /
  `week_outlook` / `deadline_risk`、既定は設定の `decision.question_set`
- `true` / `false` は `はい` / `いいえ` と表示する
- **質問セットと `choice` 型の答えは日本語で表示する。** 保存値（`next_action` / `quick_task` など）は変えず、
  表示名だけを `[ui.question_set_labels]` / `[ui.choice_labels]` から引く（`[ui.activity_labels]` と同じ方式）。
  質問ごとの指定が無ければ種別のラベルを試し、それも無ければ保存値をそのまま出す
  （`gap_activity_type` の選択肢は種別そのものなので、個別指定なしで日本語になる）
- 値が `null`（判断できない）のときは `不明` と表示する
- **保留（`confidence < threshold`）の行は控えめな見た目にし、「保留」と明示する。**
  CLI が `?` を付けているのと同じ判定
- 実際に答えたエンジン名（`エンジン: rule_based`）と所要時間を必ず出す。
  チェーンが退避して `rule_based` になった場合も分かるようにするため
- 計画の担当（`計画: offline` / `claude` 等）も併記する
- **運用方針・エンジンの上書きは画面に出さない。** 設定で決めるものであり、
  画面から都度変えられると「どの設定で出た結果か」が追えなくなるため
- 日付を切り替えると前の日の結果は消える
- **外部送信の判定は「LLM かどうか」ではなく「外部へ HTTP で送るか」で行う。**
  ローカル完結は `rule_based` のみ。`claude` / `openai_compat` は各社の API、
  `jev` は Jev Decision API へ送る（`jev` は LLM ではない）。
  画面は `GET /api/decide/info` の `sends_external` だけを見て確認ダイアログと警告を出し、
  文言は `external_engines` / `planner` から組み立てる（固定文言にすると運用方針を変えたとき
  実態と食い違うため）
- **許可リストは変更していない。** 外部へ渡るのは従来どおり `state_to_flat_dict` / `_safe_state_payload`
  が通した項目だけで、生ログ・ウィンドウタイトルは渡らない
- 判断結果は `decision_logs` へ記録される（CLI と同じ経路）
- `plan` の Markdown は **HTML へ変換せず `<pre>` でそのまま表示**する（外部ライブラリを入れない方針のため）

### 変化・判断の表示

一覧は **`時刻　案件　内容`** の順。案件が無い行でも位置がそろうよう `（未指定）` を出す
（以前は末尾に出していたため、案件が無いと何も出ず、桁もそろわなかった）。

編集欄も **時刻・案件を左端**に置く。いつ・どの案件の話かを先に決めてから内容を書く流れに合わせ、
一覧の並びとも揃える。

| | 一覧 | 編集欄 |
| --- | --- | --- |
| 変化 | `10:30　sample_project　先方のAPI利用が不可と判明` | `[時刻] [案件▼] [説明]` |
| 判断 | `11:00　sample_project　CSV連携方式に変更（API利用不可のため）` | `[時刻] [案件▼] [判断] [理由]` |

## 3.1 選択肢の設定

### 種別は日本語で表示する

**保存値は変えない。** `ActivityType` の値（`coding` など）は DB・設定・ドキュメントの契約なので不変。
表示ラベルだけを日本語にする。

既定のラベルは `config.toml` の `[ui.activity_labels]`。画面から変更した内容は
`app/data/ui_options.json` へ保存し、既定へ上書き適用する。

`config.toml` は同梱の既定値（Git 管理・読み取り専用）、画面が書き換える値は `app/data`（Git 管理外）。
画面の操作でリポジトリが汚れないようにするため分けている。

### 画面から編集できるもの

| 対象 | 編集できること | 編集できないこと |
| --- | --- | --- |
| 種別 | ラベル・並び順・表示/非表示 | 値の追加・削除（`ActivityType` はコードの契約） |
| 案件 | 表示名・並び順・表示/非表示・**表示用の案件の追加** | **リポジトリの案件フォルダの作成・変更** |
| タスク | 入力候補の編集 | `tasks.md` の変更（読み取り専用） |

**案件の正本は仕事管理リポジトリの `10_projects/`。**
画面から足した案件は contextflow 側だけの存在で、`from_repo=false` として
「リポジトリ外」と分かる表示にする。判断・変化の書き出し先（`decisions.md`）が無いため。

全種別を非表示にはできない（1つも選べなくなるため、サーバが 400 を返す）。

ラベルの入力欄を空にすると**既定へ戻る**（種別・案件で同じ扱い）。エラーにはしない。

## 4. API 契約

すべて JSON。エラーは HTTP ステータス + `{"error": "日本語メッセージ"}`。

### 参照

| メソッド | パス | 返すもの |
| --- | --- | --- |
| GET | `/api/day?date=YYYY-MM-DD` | その日の全データ（下記） |
| GET | `/api/projects` | `[{key, folder, prefix, suffix}]` |
| GET | `/api/raw?start=ISO&end=ISO` | `[{ts, process, window_title, idle_sec}]`（明示要求時のみ） |
| GET | `/api/options` | 選択肢の確定形（案件・種別・タスク候補） |
| GET | `/api/state?date=YYYY-MM-DD` | 保存済みの Current State（未作成なら `state: null`） |
| GET | `/api/decide/info` | 運用方針・質問セット・外部送信の有無 |
| GET | `/api/calendar/events?days=7` | 保存済みの予定を `uid` でまとめて返す |

`/api/day` の応答。

```json
{
  "date": "2026-09-23",
  "running": {"activity_type": "meeting", "project": "sample_project", "task": "要件整理",
              "started_at": "2026-09-23T10:45:00+09:00"},
  "collector": {"running": true, "owned_by_ui": true,
                "last_event_at": "2026-09-23T14:53:14+09:00",
                "events_in_range": 17, "interval_sec": 5, "flush_every": 12},
  "sessions":   [{"id":1,"start_at":"...","end_at":"...","process":"Code.exe","duration_sec":4320}],
  "activities": [{"id":1,"start_at":"...","end_at":"...","activity_type":"coding",
                  "layer":"confirmed","source":"windows","project":"sample_project",
                  "task":null,"summary":"Code.exe","confidence":0.9,"editable":false}],
  "gaps":       [["2026-09-23T10:12:00+09:00","2026-09-23T10:45:00+09:00"]],
  "changes":    [{"id":1,"ts":"...","description":"...","project":"sample_project"}],
  "decisions":  [{"id":1,"ts":"...","decision":"...","reason":"...","project":"sample_project"}],
  "activity_types": ["coding","research","meeting","..."]
}
```

`activities` は確定層を優先し、無ければ観測→手入力→予定の順で1層だけ返す（CLI と同じ規則）。
`editable` は「3. 編集できるもの」の判定結果。

`/api/state` の応答。

```json
{
  "date": "2026-09-23",
  "state": { CurrentState を JSON 化したもの } または null,
  "generated_at": "2026-09-23T17:05:00+09:00" または null,
  "path": "app/data/state.json"
}
```

**参照では組み立てない。** 作成するのは `POST /api/state` だけ。参照で暗黙に組み立てると
「いつ時点の状態か」が分からなくなるため。

- 保存先は2か所。`[paths] state_json`（既定 `app/data/state.json`、**毎回上書き**）と、
  SQLite の `state_snapshots` テーブル（**追記**、日付ごとに履歴が残る）
- 画面の参照は `state_snapshots` の**その日の最新1件**を読む（`StateSnapshotRepository.latest_for`）。
  `state.json` は最新1件しか持てないため、過去日の参照には使わない
- 材料は**確定層（confirmed）**の活動。無ければ観測層（observed）へフォールバック
  （`ContextBuilder._load_activities`）。手入力（reported）は `build`
  （画面の `[タイムラインを作り直す]`）を通さないと入らない

`/api/decide/info` の応答。

```json
{
  "mode": "rule_first",
  "description": "ルールベース先行。…",
  "engines": ["rule_based"],
  "planner": "offline",
  "external_engines": [],
  "planner_external": false,
  "sends_external": false,
  "threshold": 0.7,
  "default_set": "next_action",
  "sets": [{"name": "next_action",
            "questions": [{"key": "…", "type": "noul", "instruction": "…",
                           "choices": [], "min": 1, "max": 5}]}]
}
```

`sends_external` は `engines` / `planner` のどちらかが外部へ HTTP で送る場合に `true`。
画面はこの値だけを見て確認ダイアログ・警告文言を出す（「外部送信の判定」は §3 の
「判断・計画」を参照）。

`/api/calendar/events` の応答。

```json
{
  "days": 7,
  "start": "2026-09-23T00:00:00+09:00",
  "end": "2026-09-30T00:00:00+09:00",
  "events": [{"uid": "EV-REVIEW", "summary": "設計レビュー", "activity_type": "meeting",
              "labeled": false, "count": 2,
              "first_start": "…", "last_end": "…"}],
  "unlabeled": 2,
  "no_uid": 0
}
```

`labeled=false` を先、その中では `first_start` 昇順。`count` は同じ `uid` の行数
（定期予定・日跨ぎ分割で複数になる）。

`date` 省略時は今日、`time` 省略時は現在時刻。

`PUT /api/calendar/label` の応答 `{"ok": true, "uid": "…", "activity_type": "review", "updated": 2}`
（`updated` は反映した `planned` 行数）。不正な種別・`uid` 空はいずれも 400。

`POST /api/decide` の応答。

```json
{
  "ok": true, "date": "2026-09-23", "set": "next_action",
  "engine": "rule_based", "latency_ms": 3, "threshold": 0.7,
  "generated_at": "2026-09-23T17:05:00+09:00",
  "answers": [{"key": "urgency", "type": "score", "instruction": "…",
               "value": 4, "confidence": 0.62, "raw_confidence": 0.62,
               "engine": "rule_based", "rationale": "…", "held": true}]
}
```

`answers` は質問セットの**定義順の配列**（dict ではない）。`held` は `confidence < threshold`
（CLI が `?` を付けているのと同じ判定）。`POST /api/plan` は上記に `text`（Markdown 文字列）が加わる。

応答に含まれる追加キー。

| API | 追加キー | 内容 |
| --- | --- | --- |
| `POST /api/work/start` | `stopped_type` | 実行中の作業を自動終了して開始した場合、その種別（`ActivityType` の値）。無ければ `null` |
| `POST /api/work/stop` | `activities` | 日をまたいで分割された全区間の配列。`activity` は従来どおり単一（分割時は終了時刻を含む最後の区間） |
| `POST /api/work/add` | `activities` | 同上 |

実行中なし・開始直後の取り消しのときは `activities: []` とし、結果に応じた `message` を添える
（「収集・記録の状態表示」の「終了・開始メッセージの出し分け」を参照）。

## 5. 安全側の設計

| 論点 | 対応 |
| --- | --- |
| 外部から触られる | `127.0.0.1` 固定バインド。`0.0.0.0` にしない |
| 他サイトからの書き込み（CSRF） | 起動時トークンを `X-CF-Token` ヘッダで要求。`Origin` / `Host` が localhost か検査 |
| 生ログの流出 | 既定で非表示。明示要求時のみ取得 |
| `collect` との同時書き込み | WAL 有効済み。書き込み時は短いリトライを入れる |
| 誤操作 | 削除は確認ダイアログ。編集不可の層は API 側でも 409 を返す |
